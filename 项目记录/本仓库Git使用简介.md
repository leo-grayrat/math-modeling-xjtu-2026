# 本仓库 Git 使用简介

## 一句话说明

这是一份只给本项目自己看的 Git 使用说明。仓库里的 Git 不只是用来记录“做过哪些事情”，还要记录“为什么采用这个方案、为什么放弃另一个方案，以及这个结论由什么证据支持”。

本项目是数学建模项目，不是常规软件产品。数据体量大，正式计算依赖本地 MATLAB，部分数据不能上传，模型路线也经常需要比较后再决定。因此，Git 的使用要保留软件工程中有价值的部分，同时避免把所有工作机械地套成软件开发流程。

## 1. 先分清五类东西

建模过程中容易把需求、方案、代码和结果混在一起。后续尽量按下面的关系管理：

| 内容 | 适合放在哪里 | 要回答的问题 |
|---|---|---|
| 正在讨论的需求和变更 | GitHub Issue | 这次到底要解决什么，讨论到哪一步 |
| 用户追加要求、阶段进度和最终决定 | 本地 Markdown | 最后确定了什么，为什么这样确定 |
| 模型路线和取舍 | Issue 讨论、计划变更说明、PR 描述 | 为什么选它，为什么不选别的 |
| MATLAB/Python 实现 | 分支中的代码 | 具体怎样算出来 |
| 运行结果和指标 | PR 附件、`results/` 中的小型结果表 | 运行后得到了什么 |
| 稳定阶段的快照 | Tag 和 Release | 哪个版本可以退回或作为交付底稿 |

Issue 不需要把整个项目报告复制一遍。它负责中间的需求、问题和讨论；本地 Markdown 负责长期保存用户追加要求、阶段进度、计划变更和最终决定。必要时在两边写 Issue 编号或文件路径，让它们能够互相追溯。

代码不能替代需求说明，结果表也不能替代模型解释。Issue、PR、提交记录和本地阶段说明应该互相指向，而不是各写一遍互不相干的内容。

## 2. 按工作大小选择流程

不是每个改动都值得开分支。采用三级规则：

### A 类：直接提交

适用于不会改变模型结论的工作，例如：

- 修正错别字、阶段说明和 README；
- 补充工具问题记录；
- 整理已经确定的文件位置；
- 修正不影响结果的注释或输出格式。

这类工作可以直接在 `main` 上完成，但仍然要用清楚的中文提交信息，必要时注明对应的阶段。

### B 类：Issue → 分支 → PR

适用于会改变代码、结果或模型解释的工作，例如：

- 增加一个基因普遍重要性模型；
- 改变冷启动划分或验证指标；
- 比较岭回归、LASSO 等不同路线；
- 改变模块数量、特征定义或最终预测公式。

这类工作必须先写 Issue，再从 `main` 建立分支。分支完成后开 PR，把差异、结果和理由放在同一个地方，最后才合并回 `main`。正式模型、数据处理代码、评分代码和提交代码都属于这一类，即使实现只需要十分钟，也不能直接把未审查的结果写进 `main`。

### C 类：先写计划变更，再暂停

如果工作会改变已经批准的总清单，例如增加原先没有的模型、删除一个既定步骤或改变论文主线，必须先写“计划变更说明”。

在用户明确同意前只做必要的说明，不继续偷偷实现。用户暂时没有回复时，按“尚未决定”处理，不把沉默当成否决，也不当成同意。

## 3. Issue：把模糊想法变成可验收的问题

Issue 在本仓库中不只用来报 Bug，也用来保存结构化需求和研究问题。一个合格的 Issue 至少包含以下内容：

```text
标题：[实验] 新基因普遍重要性：岭回归路线

想解决的问题：
新基因没有训练标签时，能否仅凭基因元数据估计它的平均依赖性？

实际操作：
整理基因元数据，构造训练表，按“新基因”冷启动划分验证。

数学方法：
标准化特征后使用岭回归，并与基因均值基线比较。

验收标准：
1. 新基因组的官方指标高于基线；
2. 训练集和新基因验证集没有混用；
3. 结果可以由一条明确的 MATLAB 命令复现；
4. 结论和限制写入阶段说明。

不在本 Issue 内：
暂不加入细胞—基因交互，也不改动最终论文格式。

数据和隐私边界：
不上传原始数据，不在 Issue 中粘贴姓名、学号或队伍资料。
```

Issue 的重点不是把话写得像产品需求文档，而是让半年后的自己仍能回答：当时想解决什么、用了什么数据、什么结果才算成功。

提交信息或 PR 描述可以写 `Closes #编号`，让实现和需求建立链接。对于最终失败但有参考价值的路线，不要删除 Issue，而应在其中记录失败原因，并将 Issue 关闭为“未采用”。

## 4. 分支：一条可失败的模型路线

分支表示“这是一条尚未被 `main` 接受的路线”，不表示一定要开发很久。推荐使用能看懂用途的名字：

```text
experiment/issue-12-ridge-gene-prior
experiment/issue-13-lasso-gene-prior
fix/issue-15-cold-start-leakage
docs/issue-18-submission-code
```

正式模型和代码需求必须开分支；只有 A 类的记录性改动不需要开分支。分支不代表工作一定很久，它只是把尚未接受的 Diff 隔离出来。

分支中的提交可以比较频繁，方便退回和定位问题；但不要把未完成的实验结果直接合并到 `main`。在 PR 前可以在尚未推送的分支上整理明显的试错提交，但不要改写已经合并的主分支历史和正式 Tag。

## 5. PR：本仓库的“AI 审查契约”

PR 的作用不是假装有很多协作者，而是把一次路线变更的 Diff、运行证据和解释集中起来。每个正式模型分支合并前，都应填写下面这些内容：

```text
关联 Issue：Closes #12

这次改了什么：
新增基因元数据到平均依赖性的岭回归，并保留原有基线。

实际操作：
输入哪些表、如何连接、如何划分旧基因和新基因、输出哪些文件。

数学模型：
特征标准化、岭惩罚、参数选择方法，以及为什么适合这个冷启动问题。

证据：
列出基线和新模型在四类测试组上的指标，注明运行命令和随机种子。

需要质疑的地方：
是否有新基因信息泄漏？是否只在旧基因上变好？是否依赖某个本地绝对路径？

结论：
合并、继续实验，或关闭为未采用，并说明原因。
```

这份 PR 描述要强迫 AI 和未来的自己回答“为什么这样写”。当前不接入 CodeRabbit、Cursor Review 等第三方 AI 服务，也不把外部 AI 审查作为合并条件；可以在本地让 Codex 或自己按下面的问题阅读 Diff：

- 代码是否真的使用了冷启动划分；
- 训练和验证数据是否串了；
- 路径、随机种子和输出文件是否可复现；
- 论文中的数字是否能在结果表中找到；
- 注释是否说清楚实际操作和数学模型的区别。

如果将来考虑第三方审查，必须先确认代码、原始竞赛数据和未公开论文内容不会被发送到不合适的服务。这个仓库默认不把原始数据和个人信息放入远程平台。

## 6. CI 与本地检查

本项目的大型 MATLAB 计算不适合每次 PR 都在 GitHub Actions 中完整重跑。原因有三点：原始数据体量大、远程环境未必有 MATLAB 许可、完整模型运行时间和资源消耗都不稳定。

本轮不配置 GitHub Actions，也不让远程平台下载竞赛数据或尝试运行 MATLAB。所有检查先在本地完成，并在 PR 中写明命令和结果。

适合本地执行的轻量检查包括：

- Markdown 和代码文件的基本格式检查；
- `git diff --check`；
- 不允许提交明显的个人绝对路径；
- 检查提交包中没有原始数据、获奖通报、姓名和学号；
- 对不依赖大数据的辅助函数运行小型冒烟测试；
- 检查结果表的表头和必要文件是否存在；
- 检查模板和提交范围没有要求上传原始数据或个人资料。

以下重检查也保留在本地：

- 读取完整竞赛数据；
- MATLAB 工具箱检查；
- 全量模型训练和官方评分；
- 大型图表生成；
- 需要本地讲义或专用环境的实验。

PR 中不写“自动化通过所以模型正确”，而是同时放置本地运行命令、运行环境、关键指标和限制。等检查规则稳定、模型冻结后，再单独讨论是否需要轻量 CI。

## 7. Hooks：保留底线，不自动干扰研究

Git Hooks 可以作为预提交保镖，但本仓库不强制安装会自动修改文件的 Hook。建模代码和论文 Markdown 经常需要保留有意的排版、中文字符和实验中间状态，自动格式化可能制造无关差异。

如果后续需要启用，优先选择只读或失败即停的检查：

- 提交前检查空白错误和个人绝对路径；
- 推送前运行一个不读大数据的 MATLAB/Python 冒烟测试；
- 检查待提交文件名和隐私排除规则。

不要让 Hook 自动删除结果文件、自动重跑全量数据或自动修改模型参数。任何涉及结果的动作都应由人明确发起并留下提交记录。

## 8. Tag 与 Release：给重要结论建立锚点

提交记录适合记录过程，Tag 适合标记“这一刻可以作为参照”。本仓库当前不追溯创建 Tag，等核心模型冻结后再建立第一个正式锚点。之后不需要每个小提交都打 Tag，只在模型或交付真正稳定时使用。

Tag 名称可以保留本项目的版本编号习惯，例如：

```text
v2.0-model-frozen
v3.0-paper-draft
v4.0-submission
```

Tag 一旦用于比较性能或作为交付底稿，就不要重新指向别的提交。性能比较应记录在结果表中，例如比较不同 Tag 在四类冷启动组上的 Spearman、NDCG、Precision 和 RMSE，而不是只说“新版本更好”。

Release 是 Tag 的一份可下载快照。最终 Release 可以包含论文、提交代码、运行说明、必要的小型结果表和环境信息，但不应包含：

- 竞赛原始大数据；
- 2 GB 级压缩包；
- 获奖通报、队伍资料、姓名和学号；
- 只在本地有效的临时文件。

## 9. 本项目建议的实际闭环

一次正式模型改动按下面的顺序走：

```text
发现问题或提出想法
        ↓
Issue 写清目标、边界和验收标准
        ↓
若改变既定计划，先写计划变更说明并等待同意
        ↓
建立实验分支
        ↓
用 MATLAB 完成实际计算，保存小型结果表和运行命令
        ↓
提交 PR，写清 Diff、模型、指标、失败点和隐私检查
        ↓
本地轻量检查与人工阅读
        ↓
合并到 main，必要时关闭 Issue
        ↓
模型冻结后再打 Tag，阶段完成后暂停进入下一阶段
```

其中“实际操作”和“数学模型”必须分开写。比如“把 113 条末级通路读入 MATLAB”是实际操作；“用因子分析把相关通路归纳为 8 个共同因子”才是数学建模方法。PR 如果只写算法名称而不写前面的实际操作，仍然不算完整。

## 10. 当前仓库的落地顺序

本仓库当前已经有中文版本提交记录、阶段说明和计划变更说明；本次会建立 Issue/PR 模板，但不建立 Tag 或 CI。其他功能按以下顺序逐步启用：

1. 下一次正式模型路线比较时，试行一个 Issue、一个实验分支和一个 PR；
2. 模型冻结后建立第一个里程碑 Tag；
3. 提交代码整理完成后，再单独评估轻量 CI；
4. 只有当检查规则稳定、不会干扰 MATLAB 研究流程时，才评估是否启用 Hooks。

不为了“看起来像专业项目”而一次性启用所有功能。Git 的附加功能只有在它确实帮助我们解释需求、比较方案、守住数据边界时才值得保留。
