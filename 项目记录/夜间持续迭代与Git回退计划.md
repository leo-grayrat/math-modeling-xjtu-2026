# 夜间持续迭代与 Git 回退计划

## 用户追加要求（原文）

> 我再提醒一点，这期间任何改动都要做好 Git 存档，以及不同的路线。
>
> 我们很有可能要进行很多调整。很有可能你做的一百件事里，其中有 65 件都是对的，但是 35 件都要回炉重造。所以说，必须做好详实的仓库准备，我们之后可能会需要做很多回退。
>
> 请你把工作把它的耦合性拆开，不要什么都混在一块儿，否则我们之后修改会非常困难。

## 今晚的工作顺序

1. 先完成 Markdown 论文初稿，使各章节、真实结果、公式和引用能够连成完整文章。
2. 再分章节补充细节和修改表达，逐步接近终稿；没有结果支撑的内容保留明确占位，不自行编造。
3. 全文完整后，分别调用数模论文和科研写作、审稿 Skill 检查结构、论证、数字与文风。
4. 文字主线稳定后才重新尝试绘图；被否决的四张图不直接回填，新方案先保存为候选路线。

## Git 存档规则

- 把“论文正文、引用补充、审稿修改、图表重做”拆成不同 Issue、分支、PR 和提交，避免互相绑死。
- 一次提交只完成一个能够独立说明、独立比较或独立回退的小目标。章节完成、引用补齐、一次审稿修订和一组候选图分别留存节点。
- 稳定主线与探索路线分开：探索结果保留在独立分支或 PR 中，不覆盖已经可用的版本；失败路线也保留结论和原因，便于之后回看。
- 不改写已推送历史，不强制推送，不把模型结论、论文措辞和图片大批混进同一次提交。
- 每次准备进入下一类工作前，先确认当前工作区已经提交并写清楚该版本做了什么。

## 无人反馈时的边界

- 用户睡觉期间没有回复，不表示否决，也不表示允许扩大模型路线；只执行已经明确批准的论文、审稿和候选图工作。
- 能够确定的文字和整理工作继续推进；遇到需要改变模型结论、删除重要成果或在两条路线间作主观选择时，保留两个版本并等待用户决定。
- 如果出现工具小故障，先使用可靠替代方法并记录；如果缺少关键结果，则保留缺口，不用猜测填满。

这套安排默认接受“多数工作可保留、少数工作需要重做”的现实。Git 的目的不是累计提交次数，而是让后续任何一处返工都不必连带推翻整晚成果。
